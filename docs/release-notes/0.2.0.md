# CipherChat 0.2.0 (2026-11-02)

A security release of CipherChat by DarkCipher Systems, a self-hosted chat with voice and video calls where every
message, file and call frame is end-to-end encrypted with post-quantum hybrid cryptography, on your own server.

It exists to give privacy and control of conversations back to the people having them: no company in the middle, no
one else's rules, no data to sell or hand over, and open code anyone can check.

## Changes since 0.1.2

0.2.0 brings forward secrecy to room keys (protocol 1.1 and protocol 2, `docs/PROTOCOL.md` §10 and §11).

* **Room keys are sealed to each of your devices, not your identity**: every app or browser that keeps your keys is a
  device in your signed device list. Each device publishes a short-lived prekey every day and erases old ones. A new
  room key is sealed to every listed device's prekey, so someone who later gets your identity key and passphrase
  still can't open room keys from before that.
* **The server stops keeping room keys** once your devices have them: each device keeps the keys it has opened in its
  own sealed key store (the platform seals it: DPAPI on Windows, a hardware-backed key on Android, a non-extractable
  key in the browser). The device acknowledges them, and the server deletes its copy when every device has, or
  after 7 days at the latest. The server never re-wraps a room key.
* **Old database copies can't open keys**: what the server still stores is sealed under a storage key that changes
  every day, and keys older than three days are erased (`/var/lib/cipherchat-shred`, never backed up).
* **History on a new device only with your approval**: a new device asks; another of your devices shows its name and
  device code, and only after you approve there does it send your room keys, sealed to the new device. Room admins
  can set a history window (as long as messages, or 7, 30, 90 or 365 days) and switch history sync off for a room.
* **Removing a device wipes it**: a device you remove from your list erases its key store the next time it connects.
* **Warnings you can see**: a room says when a key was made in compatibility mode, when the server still keeps your
  old room keys after a week, and when a key doesn't follow on from the one before it.
* **Renew a room key yourself**: "New key now" (Windows), "Renew the key now" (Android) and `/rotate` (web), for every
  member, not only admins.
* Fixes: no stray "null" in the room header for members who aren't admins; a request from the wrong address now names
  the address to use.

## Upgrading

**Update the server first, then every app.** Everything keeps working while you do, and nothing needs to be redone
by hand.

* **The server**: unpack the release and run its `install.sh`, which offers "Upgrade to 0.2.0" (or
  `sudo sh install.sh --plan /etc/cipherchat/setup.json`). As always it copies the database first and rolls back by
  itself if the new version doesn't start. The upgrade adds `/var/lib/cipherchat-shred`: keep it out of your backups
  and disk images.
* **The web chat** updates with the server: reload the page. The first time, it asks whether to keep room keys in
  this browser.
* **Each app**: install 0.2.0 (Windows Setup or MSI, Android APK signed with the same key, so it updates in place) and
  open it once. On first unlock it moves the room keys it can open into its key store and acknowledges them.
* **Compatibility mode**: until every member's apps are updated and opened, rooms with that member get compatibility
  room keys. These are just as encrypted, but the server keeps its copy until the 7 days are up instead of until
  every device has the key. The room says so, and it ends by itself once the last old app is updated or signed out.
* **Update every app, including ones you rarely use**: a 0.1.2 app that signs in during the first 10 minutes after
  another device has acknowledged a key can miss keys it hadn't read yet. A 0.1.2 app also can't read messages sent
  under a per-device key. The server notices a 0.1.2 app that stays signed in, and the next message anyone sends
  comes with a compatibility key it can read; messages from before that stay unreadable on the 0.1.2 app.
* **Adding a device after upgrading**: it reads earlier messages only after you approve it on a device you already
  have. If you have no other device, it starts from the next room key.
* **Server admins**: once the new version has run well for a few days, delete the copies of the database made before
  the upgrade (`/var/backups/cipherchat-upgrades/<time>-0.1.2-to-0.2.0`, and nightly backups from before the upgrade
  once they're no longer needed). They still hold room keys in the old form, which the rolling storage keys can't
  erase. Since this release the server seals what it stores as it starts, so the backup taken right after the
  upgrade already has the new form.
* **Going back to 0.1.2** is only possible by restoring the database copy made before the upgrade, which loses
  everything since. Once the server has run 0.2.0, the room keys it stores are in the new form, which 0.1.2 can't read.

## Security testing

The penetration test and debug sweep in `docs/security/PENTEST-2026-10.md` now covers protocol 1.1 (`pt_22`) and
protocol 2 (`pt_23`): server functional (26), pentest (23), WebAuthn (6), web (75 history and 29 call checks), Windows
(70), Android, and cross-client fixtures and live tests. Every finding is fixed or documented: P-1 (the server can
force compatibility mode, visibly), H-1, H-3, H-4, P-2, P-4 (by design, documented), H-2 (above), P-5, P-6, P-7 and
P-8 (fixed).

## Known limits

* The Windows installers aren't Authenticode-signed yet: SmartScreen warns and Smart App Control blocks them. Check
  the SHA-256 against `SHA256SUMS`.
* A server can force compatibility mode (P-1) by withholding a prekey; the room says so when it does.
* Group calls are a mesh (up to 8 people). Mac and iOS are planned (`docs/MAC-IOS-HANDOFF.md`).
